# Recon notes (2026-11-03)

Read-only research gathered before the design. Six independent tracks; each finding lists confidence and evidence. Orca version at the time: 1.4.247 (latest release). Treat runtime claims marked medium/low as hypotheses to verify in a spike.

## Orca trusted-worker plugin capabilities: can it host a full Azure DevOps client with OAuth sign-in?

Yes, it can. A trusted-worker `main` is an ordinary `child_process.fork` of Electron's Node 24.22.1. It has no permission flags and no network allowlist. So `fetch` to dev.azure.com and login.microsoftonline.com works, as do a 127.0.0.1 loopback server, `crypto` and `child_process`. MSAL Node (needs Node 20 or later) can run auth code + PKCE over a loopback redirect, or device code. Tokens go in `orca.secrets`: Electron safeStorage, a Keychain-backed key, up to 64 KiB per value. Panels have no network, so every ADO call has to go through the worker, using `plugin.request` (answers up to 1 MiB) and `panels.post` (up to 256 KiB, 200 per 10 s). Version is the main constraint. The installed Orca is 1.4.247 and refuses any plugin whose `engines.orca` is above that. That rules out hooks (including injecting text into agent prompts), status bar items, `workspace:write`, `agent:launch` and `terminal:read` until 1.4.248 ships. Lifetime is the second constraint. The worker starts lazily and is reaped after 5 minutes idle, and commands time out after 30 s, so sign-in must not be awaited inside a command. Orca also has a built-in ADO PR integration, but it only reads `ORCA_AZURE_DEVOPS_*` environment variables, so a plugin cannot pass its token to it.

### Findings

**1. Can the worker reach dev.azure.com and login.microsoftonline.com? Which Node built-ins can it use? Is it sandboxed?** _(confidence: high)_

There is no sandbox and no network allowlist or capability. The worker is `child_process.fork(plugin-host-entry.js)` with `execArgv: []`, `ELECTRON_RUN_AS_NODE=1` and IPC. It runs Node 24.22.1 / Electron 43.8.4, global `fetch` exists and `process.permission` is absent. The module loader hooks only transpile .ts files and refuse runtime imports of `orca`. Everything else resolves as normal Node: http/https, `net` (so a 127.0.0.1 loopback server works), `crypto`, `child_process` and `fs`. Orca itself describes the profile as 'Runs its own code in a separate Node.js process on the Orca host, with your user account's access'. One catch: the child's environment is cut down to a whitelist (PATH, HOME, LANG/LC_*, TZ, TMPDIR/TEMP/TMP, plus Windows vars). HTTPS_PROXY, NO_PROXY, NODE_EXTRA_CA_CERTS and SSL_CERT_FILE are dropped. Panels, by contrast, are network-denied at the session level, so all ADO traffic has to live in the worker.

Evidence: /Applications/Orca.app/Contents/Resources/app.asar (out/main/index.js, offset ~5655841): the env whitelist and `fork(i,[],{env:lVr(),execArgv:[],serialization:'advanced'})`; app.asar.unpacked/out/main/plugin-host-entry.js (loader hooks only); `ELECTRON_RUN_AS_NODE=1 Orca -e` printed 24.22.1 43.8.4, fetch available, no permission model; `orca plugin inspect` executionDescription; docs/reference/plugin-isolated-frames.md (stablyai/orca@ec7da75)

**2. Does the worker stay alive for background polling? What restarts or kills it?** _(confidence: high)_

Start: lazily, on a command, an event listed in contributes.events, a panel `plugin.request` or a hook. Startup limit: `activate` must signal ready within 10 s. Idle reaping: a 60 s sweep stops a worker that has no calls in flight and no activity for 5 min, and `deactivate()` gets 2 s before SIGKILL. 'Activity' covers worker→host calls, `panels.post`, responses and event deliveries, so a timer that makes any host call more often than every 5 min keeps the worker alive. That behaviour is not documented. Plugins that declare any contributes.hooks are `keepWarm` (never reaped) and are started as soon as the plugin set changes, including at Orca launch. Hooks need 1.4.248. Timeouts: commands 30 s (handler `signal` aborts), panel requests 30 s by default and 120 s at most, event handlers 300 s, hooks 2 s; more than 64 pending events kills the worker. Crashes: up to 3 restarts (backoff 0.5 s, 2 s, 5 s), then the plugin is marked 'errored'. Saving a file in a dev folder restarts the worker and drops its memory. At most 5 workers run at once.

Evidence: out/main/index.js: `idleReapMs??3e5` and `reapIdle` skipping `spec.keepWarm`; `B7` sets keepWarm when `contributes.hooks.length>0`; `LBr` calls ensureWorker for hook plugins; housekeeping `setInterval(reapIdle,6e4)`; `readyTimeoutMs??1e4`, `invokeTimeoutMs??3e4`, `eventTimeoutMs??3e5` (hVr), gVr=64; `iVr={maxRestarts:3,backoffMs:[500,2e3,5e3]}`; `maxActive??5`; recipes.md ('An idle worker stops and restarts on its next command, event or panel request')

**3. What do the secrets, storage and settings APIs look like, what backs them, and how are they scoped?** _(confidence: high)_

Secrets (`secrets:own`): `orca.secrets.get/set/delete` take string values only, plus `host.call('secrets.protection')` returning 'os-keyring' or 'unavailable'. The backend is Electron safeStorage: `<userData>/plugins-data/<pluginKey>/secrets.json.enc`, format 'electron-safe-storage-v1', with the encryption key in the macOS Keychain. Limits: 65,536 characters per value, 1,024 keys, 5 MiB file. Secrets are per plugin, shared by its worker and its own panels/editors. Writes are audit-logged by key name only. Storage (`storage:own`): JSON, at most 256 KiB per value and 1,024 keys. A storage.json over 5 MiB reads back as {} (silent data loss risk), so storage is unsuitable as a big cache. It is shared with panels, `onDidChange` fires on every surface, and components atoms can use `persist: 'storage'`. Settings (`settings:own`): declared in contributes.settings (string, number, integer or boolean; enum and enumLabels; multiline; placeholder; up to 64), edited in Orca Settings, read and written with `settings.get/set`, with `onDidChange` including changes the person makes. Caches and token-cache files belong under HOME or TMPDIR, never in the plugin folder: its content hash is verified before every spawn.

Evidence: out/main/index.js: class `x7` (secrets: `DS.encryptString`, `secrets.json.enc`, 1024 keys, 5242880 bytes), class `jU` (storage: 262144 bytes per value, 1024 keys, 5 MiB file, returns {} when larger), `nBr` services map; plugin-host-api-CVXN4YFp.js (`secrets.set` value max 65536); `verifyBeforeSpawn: contentVerifier.verifyNow` in kVr.ensure; host-api.md

**4. Can the worker or a panel open the system browser for sign-in? How can the redirect be received (loopback, deep link)? Is device code an option?** _(confidence: high)_

`shell.openExternal` is for panels and editors only. It needs a click or key press on a settled control and accepts http, https and mailto. The first time a plugin opens a given host, Orca shows a dialog with an 'Always allow <host> for this plugin' checkbox (saved in settings under `pluginExternalHostGrants`). It is limited to 3 calls per 10 s and fails while the window is hidden. The worker is plain Node, so it can also run `/usr/bin/open <url>` itself without Orca's consent dialog. Deep links: Orca registers `orca://`, but only skill sharing, plugin install links and pairing are routed. Nothing reaches a plugin, so the redirect has to be a loopback (`http://localhost:<port>`) server in the worker. MSAL Node's `acquireTokenInteractive({openBrowser})` does exactly that. For device code, the worker gets the user code, `panels.post`s it to the panel, and a panel button opens microsoft.com/devicelogin. Both login flows take longer than the 30 s command timeout, so start the flow, return at once, and post an `auth.changed` event when it completes.

Evidence: out/main/index.js `l8e` (consent dialog, `pluginExternalHostGrants`) and `f8e={maxMessages:3,perMs:1e4}`; `Lee`/`Fee` (orca:// accepts only skills/share and plugin install links); Info.plist CFBundleURLSchemes=[orca]; MSAL Node docs lib/msal-node/docs/request.md ('The only required parameter is an openBrowser callback'; acquireTokenByDeviceCode); npm @azure/msal-node 7.1.2 engines node>=20

**7. What can the worker read about the active workspace: repo path, branch, remote URL, workspace ids (to map the current branch to its PR)?** _(confidence: high)_

`workspace.readContext` and the `workspace.changed` event return only {branch, displayName, terminals}: no id, no path, no remote. `workspace.list` (`workspace:read`, host API 1.3, which this 1.4.247 build exposes) returns {id, kind, name (same as displayName), path, branch, hostId} for up to 500 workspaces. `workspace.created` returns {workspaceId, kind, path, branch}. To map the focused workspace, match displayName+branch against `workspace.list`; two workspaces with the same name and branch would be ambiguous. Orca does not expose the remote URL to plugins, so the worker runs `git -C <path> remote get-url origin` itself. That only works for local workspaces: a non-null `hostId` means the files live on another host. Orca's own code already parses dev.azure.com, *.visualstudio.com and ssh.dev.azure.com/v3 remotes for its built-in review feature.

Evidence: orca-host.d.ts @ec7da75 (readContext and workspace.list result types); out/main/index.js `vBr['workspace.list']` (name = displayName, path, branch, hostId) and `nBr.resolveActiveWorktreeContext` (worktreeId kept internal); events.md

### Constraints

- Installed Orca is 1.4.247 and refuses to load any plugin whose engines.orca is above it. Hooks, statusBarItems, workspace:write, agent:launch, terminal:read and `replaces` all need >=1.4.248.
- Panels have no network: every ADO/Graph call runs in the worker. Panel requests answer at most 1 MiB; worker posts are at most 256 KiB and 200 per 10 s.
- Commands time out after 30 s and panel requests after 30 s by default (120 s at most). activate() must be ready within 10 s. Never await an interactive login inside a command or request.
- The worker is reaped after 5 min idle unless the plugin declares a hook (hooks make it keep-warm and eagerly started, 1.4.248+). Background polling is only guaranteed while it is active.
- Secrets are strings of at most 64 KiB each (1,024 keys, 5 MiB vault), encrypted with Electron safeStorage. Storage values are at most 256 KiB, and a store file over 5 MiB reads back empty.
- The worker must not write into its own plugin folder (content hash is checked before each spawn). Caches go under HOME or TMPDIR.
- The worker environment is a whitelist: HTTPS_PROXY, NO_PROXY and NODE_EXTRA_CA_CERTS are stripped. A proxy or custom CA must be handled in code.
- shell.openExternal is panel-only, needs a user gesture, asks consent per host and allows 3 calls per 10 s. orca:// deep links cannot reach plugins, so the OAuth redirect must be a loopback server in the worker.
- Workspace context lacks path, id and remote URL. Match readContext against workspace.list and run git locally; remote-host workspaces (hostId set) cannot be read with local git.
- terminal.sendText only reaches terminals in the focused workspace; text, command and prompt are each at most 4,096 characters.
- At most 4 contributes.events, 5 concurrent workers, 2,000 files and 50 MiB per plugin. Sidebar cards, task sources, connections, MCP servers and skills are reserved.
- Orca's built-in ADO PR integration only takes tokens from ORCA_AZURE_DEVOPS_* env vars in the Orca process, so the plugin cannot share its token with it.

### Recommendation

A full ADO client with OAuth is feasible as a trusted-worker plugin. Build it like this:

1. **Worker:** a `main.mjs` bundled with esbuild, including @azure/msal-node as a public client. Sign in with authorization code + PKCE through `acquireTokenInteractive`. Its `openBrowser` callback either spawns `open` or posts the URL to the panel, where a click calls `shell.openExternal`. The redirect lands on a loopback server. Keep device code as a fallback and the Azure CLI token as a second fallback.
2. **Token storage:** keep the serialized MSAL cache in `orca.secrets` through a cache plugin. Put larger API caches in a file under HOME or TMPDIR, never in the plugin folder.
3. **UI:** one components panel (or a few). It talks to the worker only through `plugin.request`, which should return quickly, and `panels.post`, which carries auth state and live updates.
4. **Long operations:** never await sign-in or long work in a command handler or request. Start it, then post the result.
5. **Ship order:** target `engines.orca >=1.4.247` now, with workspace:read, terminal:send, notifications:show, storage/secrets/settings and agent:read. Use `workspace.changed` plus panel opens to wake the worker and poll while it is active. Add a v2 manifest once Orca updates to 1.4.248: status bar items for PR and build state, an observe-only hook so the worker stays warm, and `agent.prompt.before`, `agent.launch.before` or `agent.launch` to feed work-item context to agents.
6. **Branch to PR:** find the focused workspace in `workspace.list` by matching readContext's displayName and branch, then read the remote with `git remote get-url` and query ADO by `sourceRefName`. Before relying on that path, check PATH and the proxy setup.

## Orca plugin UI surfaces vs the five ADO jobs (PR review, own-PR status, boards, wiki, pipelines)

Plugin UI can appear in two places. The first is right-sidebar panels: up to 64 per plugin, each its own activity-bar tab, 220px wide up to almost the full window. The second is custom editors, which take a full editor tab but only for a real or untitled file with the plugin's extension. Virtual documents are not supported. Components panels give native-looking lists, tables, trees, tabs, forms, Markdown and highlighted CodeView, including the `diff` and `log` grammars. They have no diff viewer, drag-and-drop, menus, dialogs, remote images or clipboard. Content is capped at 64 KiB per Markdown or CodeView and 5000 nodes per panel. HTML panels and custom editors run in isolated frames with their own DOM and bundled libraries, but no network. All data comes from the worker over `plugin.request`. That rules out a drag-and-drop board or an inline-comment diff in components, but they work in an HTML frame, best as a full-tab custom editor. Big blocker: `editor.open`, `workspace:write`, hooks, status-bar items and `frame:"isolated"` all need `engines.orca >=1.4.248`. The installed 1.4.247 is the latest release (2026-11-03) and refuses such plugins at load. Orca already has native Azure DevOps PR support (lookup, statuses, create) and a branch-compare diff.

### Constraints

- Panels have no network: every ADO call goes through the trusted-worker main (a Node child process) over plugin.request (answer up to 1 MiB, 30 s default and 120 s max timeout) and orca.panels.post (256 KiB, 200 per 10 s).
- Frame-to-host messages are capped at 64 KiB each and 120 per 10 s, so large payloads sent from a panel or editor (such as a wiki page save) must be chunked.
- Components panels: 5000 nodes, 512 KiB tree, 16 KiB per text, 64 KiB per Markdown or CodeView, 5000 Table rows, 2000 Tree items, 500 Select options; no DnD, dialogs, menus, diff view, line click, remote images or styling.
- Image and Markdown images accept only plugin-bundled .png/.jpg/.webp files, so avatars and wiki attachments need an HTML frame using data: or blob: URLs supplied by the worker.
- Panels live only in the right sidebar (220px up to window width minus about 360px); full-tab UI requires a custom editor bound to a real or untitled file with the plugin's suffix, and the editor never learns the file path.
- No API reveals or focuses a plugin panel, and none opens Orca's diff viewer; editor.open is the only official way to open a tab.
- editor.open, workspace:write, hooks (editor.save.before), statusBarItems, customEditors.frame, terminal.read and agent.launch need engines.orca >=1.4.248, and installed and latest Orca is 1.4.247, which refuses such plugins at load.
- shell.openExternal needs a user press on a control settled for about 500 ms; there is no clipboard API.
- The isolated-frame CSP forbids eval (wasm-unsafe-eval and blob: workers are allowed); a frame script or module may be about 10 MiB, and the whole plugin at most 2000 files / 50 MiB.
- Storage values are capped at about 256 KiB, so large caches (logs, diffs) belong in worker memory or on disk, not in orca.storage.

### Recommendation

Build one trusted-worker plugin with a components panel as the hub in the right sidebar. It should have Tabs for My PRs, Reviews, Work items, Pipelines and Wiki, an atom-based list-to-detail router persisted per workspace, and worker posts for live status. Use native components wherever a list, table or tree with badges is enough: PR status, approvals and policies, build trees with CodeView log tails, work-item details with a 'Move to' Select, and read-only wiki Markdown. Put the two rich jobs in custom editors so they get a full tab. (1) The board: an HTML or TS frame with real drag-and-drop, opened from a contributes.newFiles 'ADO Board' entry so it works on 1.4.247. (2) PR review: for the diff, prefer Orca's native branch compare on a worktree of the PR branch (base ref set to the target). The panel or a review editor then owns threads, votes and inline-comment entry; write a frame-based diff renderer only if native compare plus manual line anchoring proves too clunky. For the wiki, use `.adowiki.md` files: a custom editor shows status and Publish/eTag conflicts, Source gives native editing, and the worker syncs through plugin.request, chunked past 64 KiB. Set engines to >=1.4.247 now, gate editor.open, the status-bar build badge and the save hook behind a 1.4.248 follow-up, and feature-detect with host.has and ui.has. Complement Orca's native azure-devops PR status rather than duplicating it.

## What Orca 1.4.247 already does for Azure DevOps and ticket-driven work, so the ADO plugin adds to it instead of duplicating it

Orca's built-in Azure DevOps support only covers your own PR for each workspace. It finds the PR for a workspace's branch, and you can link one by URL. The sidebar card and the Checks tab show its number, title, state, merge conflicts and one combined status colour. Source Control can create the PR (title, body, draft, template, AI-written fields). There are no PR lists, diffs, comment threads, reviewer votes, approve/reject, Boards, wikis, pipelines or Teams sharing. Only GitHub and GitLab get Orca's richer review UI. Authentication is a single global token read from an `ORCA_AZURE_DEVOPS_*` environment variable in Orca's main process. There is no sign-in form, and a plugin can't set or refresh that token. The Tasks page, ticket-to-workspace flows and agent CLIs (`orca jira`, `orca linear`) are hard-wired to GitHub, GitLab, Linear and Jira. Plugin task sources and connections are reserved, and Orca rejects ADO work-item URLs as workspace references. So Boards needs its own plugin panel. To connect to Orca, the plugin can attach ADO PR URLs as references (Orca accepts those) and create worktrees and launch agents. Creating worktrees means calling the `orca` CLI from the worker, because the host API cannot create worktrees or write references. The host-API `agent.launch` needs Orca 1.4.248 or later; you have 1.4.247.

**3. Can a plugin read or write workspace references, create worktrees or workspaces, or launch agents?** _(confidence: medium)_

Through the host API: partly. **4. Could an Entra token from the plugin power Orca's native PR features, and could a plugin set ORCA_AZURE_DEVOPS_ACCESS_TOKEN?** _(confidence: high)_

In principle yes: ORCA_AZURE_DEVOPS_ACCESS_TOKEN is sent as `Authorization: Bearer <token>`, which ADO accepts for Entra tokens. In practice no, because a plugin can't get it into the place Orca reads it from. The variable is read from the Electron main process's `process.env`. The plugin worker is a separate forked process with an allowlisted environment, so it neither receives ORCA_AZURE_* nor can change the parent's environment. The only environment injection a plugin has is the `agent.launch.before` hook, and that affects agent terminals only. Entra access tokens also expire after roughly an hour, while Orca expects a fixed variable and asks for a restart when it changes. Native features can only be fed from outside, for example a PAT set before Orca starts, and that PAT then applies to every org (yours only works for <primary-org>). The plugin should run its own ADO client and not rely on native authentication.

(3) Boards: not covered (no work items, columns, swimlanes, details or state changes). (4) Wikis: not covered. Evidence: No `_apis/build`, `_apis/pipelines`, `_apis/wit`, `_apis/wiki` or `_apis/policy` strings and no Microsoft Teams references in out/main, out/renderer/assets or the extracted app.asar main/index.js; RPC namespace list from orcad-migration-source-retention-GUX0kn8S.js; the ChecksPanel and TaskPage findings above.

### Constraints

- No plugin entry into Orca's Tasks page or Settings → Integrations. Task sources, connections and sidebar cards are reserved and must stay empty, and the task provider list is hard-coded to github, gitlab, linear and jira. - Whether an `orca` CLI process started from a plugin worker (forked environment: PATH, HOME, ELECTRON_RUN_AS_NODE) can authenticate to the local runtime and run `worktree create`, `reference add` and `worktree list`.
- Whether Orca 1.4.247 refuses a plugin with engines.orca >=1.4.248 (expected from the manifest docs), and when 1.4.248 ships.

### Recommendation

Build on top of Orca's native ADO support rather than replacing it. Leave per-workspace PR detection, the sidebar PR badge, the Checks header and 'Create PR' to Orca, and offer an optional 'also set ORCA_AZURE_DEVOPS_TOKEN' hint for people who want them. The plugin should cover the gaps: (1) a PR inbox for others' PRs with diff and threads, comment, and approve/reject votes; (2) an own-PR view with reviewers and votes, policy evaluations including build validation, comments, plus copy link and share to Teams (`shell.openExternal` to a Teams deep link, or Graph later); (3) Boards with work items, columns and swimlanes, details and state moves; (4) wiki read and edit; (5) pipeline runs, timelines and logs. All of it runs on the plugin's own OAuth (Entra) token, kept in plugin secrets, with one connection per org. Connect it to Orca by attaching ADO PR URLs to workspaces as references (`orca reference add`), and by offering 'Start workspace from work item or PR' that runs `orca worktree create --reference <pr-url> --agent … --prompt …` from the worker. The terminal-command version is the documented fallback; check that the CLI route works first. Store work item ↔ workspace mappings in plugin storage. Target engines >=1.4.247 now, using only `workspace:read`, `storage`, `secrets`, `settings`, `notifications` and `terminal:send`. Add `agent.launch`, `workspace.open` and `commands.run` (to open Orca's Checks tab) once 1.4.248 is installed.

## OAuth sign-in to Azure DevOps (and Microsoft Graph) from an Orca trusted-worker plugin, late 2026

Use Microsoft Entra ID with MSAL Node, auth code + PKCE over a loopback redirect, running in the plugin's Node worker. Azure DevOps OAuth (app.vssps) has refused new registrations since 2025-04-23 and is being removed in 2026, so it is not an option. You need your own Entra app registration: public client, "Mobile and desktop" platform, redirect http://localhost, multitenant. An anonymous probe showed the three orgs sit in three different Entra tenants:
- <primary-org>: <tenant-a>, the <company-domain> tenant
- <org-b>: <tenant-b>
- <org-c>: <tenant-c>
Each org needs a token issued by its own tenant's authority. Plan for one account plus a token cache with one authority per org, not "one sign-in". MSAL 7.1.2 bundles into a single ESM file (536 KB, 230 KB minified) and runs under Orca's worker Node 24. The panel can't open URLs or reach the network itself. The worker generates the auth URL, the panel opens it with shell.openExternal on a button press, and the worker posts the result back. The worker is reaped after 5 minutes idle, so the MSAL cache must persist in orca.secrets (64 KiB per key). Graph/Teams uses the same app and refresh token with a separate per-resource token. Fallbacks: Azure CLI tokens (documented by Microsoft for ad-hoc use) and per-org PATs. Don't reuse Microsoft's first-party client IDs.

**2. Entra scopes, refresh tokens and lifetimes for the ADO resource; do all needed REST areas accept an Entra bearer token?** _(confidence: high)_

Resource app id 499b84ac-1321-427f-aa17-267ca6975798 (URI https://app.vssps.visualstudio.com). On the v2 endpoint, scopes must carry the resource prefix, e.g. '499b84ac-…/vso.work_write'; a bare 'vso.code_full' gets invalid_scope. Options:

**3. Which flow suits a sandboxed panel plus a Node worker: auth code + PKCE with loopback, device code, or the macOS broker?** _(confidence: high)_

Use auth code + PKCE with a loopback redirect.
How MSAL 7.1.2 does it: acquireTokenInteractive starts a loopback server on 127.0.0.1 with a random port, uses redirect http://localhost:<port> and response_mode=form_post, then calls your openBrowser(url) callback and waits. The listener has no timeout of its own; you can supply a custom loopbackClient. Entra ignores the port on localhost redirects, so registering `http://localhost` under 'Mobile and desktop applications' covers every port.
How it fits Orca:
- The worker is a plain child_process.fork of Electron-as-Node (Node 24.22.1, global fetch), with no permission flags, so it can listen on loopback, call fetch and spawn processes.
- Only a panel can call shell.openExternal, and only after a click or key press. The first time per host, Orca asks the person to confirm ('<plugin> wants to open login.microsoftonline.com', with an 'Always allow' option).
- plugin.request times out after 30 s by default, 120 s at most. So return the URL quickly and push completion with orca.panels.post.
- The other way to open the browser is to spawn `/usr/bin/open` in the worker, as Microsoft's azure-devops-mcp does with the `open` package.
Device code: needs 'Allow public client flows' = Yes. Microsoft recommends tenants block it with Conditional Access, and a blocked session is 'protocol tracked' through later refreshes. Keep it as an opt-in fallback only.
macOS broker (Enterprise SSO via Company Portal): needs the device enrolled in Company Portal, which isn't installed on this Mac. It also needs @azure/msal-node-extensions, whose native @azure/msal-node-runtime is about 46 MB unpacked against Orca's 50 MiB plugin cap, plus the msauth.com.msauth.unsignedapp://auth redirect, and it has no browser fallback. Not suitable.

Evidence: msal-node 7.1.2 dist/client/PublicClientApplication.mjs and dist/network/LoopbackClient.mjs (read locally); learn …/entra/identity-platform/reply-url (port ignored, prefer 127.0.0.1, IPv6 unsupported); …/scenario-desktop-app-configuration (http://localhost; public client flows only for device code, IWA, ROPC); …/v2-oauth2-device-code; …/identity/conditional-access/concept-authentication-flows ('recommends blocking device code flow'); …/msal/javascript/node/brokering-macos and /brokering; Orca app.asar out/main/index.js (fork with execArgv [], env allowlist plus ELECTRON_RUN_AS_NODE; openExternal consent dialog and pluginExternalHostGrants); Orca references/host-api.md and recipes.md (30 s / 120 s timeouts)

- New Azure DevOps OAuth (app.vssps) registrations have been impossible since 2025-04-23 and the platform is removed in 2026. An Entra app registration (or reuse of a first-party client id) is required.

- The loopback redirect must be registered as http://localhost under 'Mobile and desktop applications'; Entra ignores the port and doesn't support [::1]. Device code additionally needs 'Allow public client flows' and is commonly blocked by Conditional Access.

- User-consent policy in each tenant (Microsoft-managed default vs verified-publisher-only vs disabled), and whether <company> lets users register apps. This decides whether an admin must register the app or grant consent.
- Whether the <company> account is a B2B guest in the <org-b> and <org-c> tenants (silent cross-tenant tokens) or has separate identities (separate interactive sign-ins), and whether those tenants allow consent to an external multitenant app.
- Whether any tenant's Conditional Access requires a compliant or Intune-enrolled device for Azure DevOps. Company Portal is not installed on this Mac, so such a policy would block a browser sign-in.

- Whether a sign-in that takes over 5 minutes survives the worker idle reaper without the worker making periodic host calls.
- Serialized MSAL cache size for about 3 tenants × 2 resources (with or without access tokens) against the 64 KiB secret cap.
- Whether a browser resolving 'localhost' to ::1 hits MSAL's loopback server, which is bound to 127.0.0.1 (msal-node issue #6657 reports 'connection refused'). A custom loopbackClient may be needed.
- Whether `az account get-access-token` can mint Graph tokens with ChannelMessage.Send through Azure CLI's first-party client.
- The exact shutdown date of the legacy Azure DevOps OAuth platform (only '2026' is published).

### Recommendation

Build the sign-in on Entra ID with MSAL Node 7.x, bundled into the worker. Register one multitenant public client app (ideally owned by <company>): redirect http://localhost, granular ADO delegated scopes (vso.profile, vso.project, vso.work_write, vso.code_write, vso.build_execute, vso.wiki_write, vso.identity), and Graph User.Read plus ChannelMessage.Send/ChatMessage.Send only if in-app Teams posting is wanted. Ask a <company> admin for tenant-wide consent. Make the client ID a plugin setting.

Flow:
1. The panel's 'Sign in' calls a worker handler.
2. The handler starts acquireTokenInteractive. Its openBrowser posts the URL to the panel, or spawns /usr/bin/open.
3. The panel opens the URL with shell.openExternal.
4. The worker posts the result back.
5. The token cache lives in a custom ICachePlugin over orca.secrets, sharded per account.

For each configured org, resolve its tenant once with an anonymous HEAD to vssps.dev.azure.com/{org} and cache it. Request tokens with authority login.microsoftonline.com/{tenant}: try acquireTokenSilent first, and only go interactive for that tenant when it fails. Show per-org sign-in state in the panel.

Fallback order:
- Azure CLI tokens via `az account get-access-token --resource 499b84ac-… --tenant <tid>`: zero setup, good for day one before the app registration exists.
- Per-org PATs in orca.secrets.
- Device code only behind an explicit 'can't open a browser' option.

Skip the macOS broker. Don't ship with Azure CLI's or any other Microsoft first-party client ID. For 'send PR to seniors', start with the Teams chat deep link, which needs no consent, and add Graph posting only if users ask for it.

## Azure DevOps REST API coverage (api-version 7.1) for an Orca ADO plugin: Boards, PRs, Pipelines, Wikis, identity, rate limits, push options

The REST API covers all five jobs. api-version 7.1 is the latest GA; 7.2 is preview only. A few needed calls are preview even under 7.1: work-item comments (7.1-preview.4), policy evaluations (7.1-preview.1), Graph search (7.1-preview.1) and Markdown comments (7.2-preview.4).

Five gaps shape the design:
1. **No documented org-wide PR list.** The plugin has to call `{project}/_apis/git/pullrequests` once per project, filtering with the user's org-specific id from connectionData.
2. **No unified-diff endpoint.** The worker fetches both file versions (iteration changes give the old and new blob ids) and computes the diff itself, or uses the undocumented preview `filediffs` call.
3. **Board columns are per team.** Moving a card writes that team's `WEF_<guid>_Kanban.Column` field (plus `.Done` for split Doing/Done columns) together with `System.State`. `System.BoardColumn` is read-only.
4. **No push channel a desktop app can use.** Service hooks need a public endpoint and project-admin rights, and there is no documented SignalR. So the plugin polls, within 200 TSTU per sliding 5 minutes, and should watch the Retry-After and X-RateLimit-* headers.
5. **Every image needs the user's sign-in.** Avatars, wiki `.attachments` images and images inside work items all have to be fetched by the trusted worker and handed to the sandboxed panel, which has no network.

Pipelines should use the Build API (filters, timeline, logs by line range). The Pipelines API is only needed to start runs with parameters.

### Findings

**Boards: how to query work items assigned to me, including @CurrentIteration and team context?** _(confidence: high)_

Query: `POST https://dev.azure.com/{org}/{project?}/{team?}/_apis/wit/wiql?$top=&api-version=7.1` with body `{query}`.
- Project and team are both optional, so `[System.AssignedTo] = @Me` can run org-wide across projects.
- `@CurrentIteration` resolves against the team in the URL. The WIQL docs also show the form `@CurrentIteration('[Project]\\Team')`.

The result holds only ids (`workItems[].id`). Load the fields with `POST {org}/_apis/wit/workitemsbatch` (body `{ids (max 200), fields[], $expand: none|relations|fields|links|all, errorPolicy: omit}`).

Limits:
- WIQL text is capped at 32K characters.
- Results are cut off at 20,000 items with no error.
- Queries should finish in under 30 s.
- Microsoft recommends scoping queries to a project. Running WIQL and per-item GETs is the top cause of rate limiting.

**Boards: work item details, description/acceptance criteria, comments, linked PRs/branches** _(confidence: high)_

Details: `GET {org}/{project}/_apis/wit/workitems/{id}?$expand=all`. This returns fields, relations[] and rev.

Description and acceptance criteria:
- `System.Description` and `Microsoft.VSTS.Common.AcceptanceCriteria` are HTML by default.
- Some items use Markdown. The top-level `multilineFieldsFormat` object marks which fields.

Comments:
- List: `GET .../wit/workItems/{id}/comments?$top&continuationToken&$expand=renderedText|reactions|all&order=asc|desc&api-version=7.1-preview.4`

- Edit: `PATCH .../comments/{commentId}`

Links are relations[] entries:
- PR: `rel:'ArtifactLink'`, `url: vstfs:///Git/PullRequestId/{projectId}%2F{repoId}%2F{prId}`, `attributes.name: 'Pull Request'`. The PR's `artifactId` gives this url already built.
- Branch: `vstfs:///Git/Ref/{projectId}%2F{repoId}%2FGB{branch}`, name 'Branch'.

- Parent/child and other work-item links: `GET {org}/_apis/wit/workitemrelationtypes`.
- Reverse lookup from a PR: `GET .../pullRequests/{id}/workitems`.

**Boards: columns and swimlanes, and how to move an item (State vs board column, Doing/Done split)** _(confidence: medium)_

Reading the board:
- `GET {org}/{project}/{team}/_apis/work/boards` lists boards.
- `GET .../boards/{id or backlog level name e.g. 'Stories'}` returns:
  - `columns[]`: name, columnType (incoming/inProgress/outgoing), isSplit, itemLimit, and `stateMappings {WorkItemType: State}`
  - `rows[]`: the swimlanes
  - `fields {columnField, rowField, doneField}`: the team-specific `WEF_<guid>_Kanban.Column`, `..._Kanban.Lane` and `..._Kanban.Column.Done`
- `.../boards/{board}/columns` and `/rows` return the same parts on their own.
- `System.BoardColumn`, `System.BoardColumnDone` and `System.BoardLane` can be queried but are read-only. When several teams claim an item, the team with the longest area path decides them.

Moving a card: `PATCH {org}/{project}/_apis/wit/workitems/{id}?api-version=7.1`, Content-Type `application/json-patch+json`.
- Change state: `/fields/System.State`.
- Move column: `/fields/{columnField}`, plus `/fields/{doneField}` true/false for split columns. This also works between two columns mapped to the same state.
- Change lane: `/fields/{rowField}`.
- To move across states, take the new state from `column.stateMappings[type]` and send it with the WEF column field in one patch.
- Add `{op:'test', path:'/rev', value:N}` to catch conflicting edits.
- `?validateOnly=true` checks a patch without saving it.

Sprint taskboard (a separate mechanism):
- `GET {team}/_apis/work/taskboardcolumns`
- `GET {team}/_apis/work/taskboardworkitems/{iterationId}`
- Move: `PATCH .../taskboardworkitems/{iterationId}/{workItemId}` with `{newColumn}`

There is no 'board items' endpoint. To fill a board, use `GET {team}/_apis/work/backlogs/{backlogId}/workItems`, or WIQL on the team's area (`/work/teamsettings/teamfieldvalues`).

**PRs: list PRs where I'm reviewer or creator, across a project and across the org** _(confidence: medium)_

Listing:
- Per project: `GET {org}/{project}/_apis/git/pullrequests?searchCriteria.reviewerId={id}|searchCriteria.creatorId={id}&searchCriteria.status=active|completed|abandoned|all&searchCriteria.repositoryId&targetRefName&sourceRefName&minTime&maxTime&queryTimeRangeType&$top&$skip&api-version=7.1`.
- Per repo: `.../git/repositories/{repo}/pullrequests`.
- Project is marked required, so there is no documented org-wide list. Loop over `GET {org}/_apis/projects`, as GitLens does.
- A single PR by id works org-wide (project optional): `GET {org}/_apis/git/pullrequests/{id}`.

Which id to filter with:
- Use the org identity from `GET {org}/_apis/connectionData` → `authenticatedUser.id`.
- Do not use the profile id from `profile/profiles/me`. For some work accounts it differs and the filter returns 0 PRs.

**PRs: reviewers and votes, adding required/optional reviewers** _(confidence: high)_

Vote, or add one reviewer:
- `PUT {org}/{project}/_apis/git/repositories/{repo}/pullRequests/{prId}/reviewers/{reviewerId}` with `{vote, isRequired}`. The docs describe it as 'Add a reviewer to a pull request or cast a vote'.
- Vote values: 10 approve, 5 approve with suggestions, 0 no vote, -5 waiting for author, -10 reject.
- To vote, `reviewerId` is the user's own id.

Other calls:
- Bulk add: `POST .../reviewers` with `IdentityRef[]`.
- `PATCH .../reviewers/{id}` can only change `isFlagged` and `hasDeclined`.
- Reviewer objects carry `isRequired`, `hasDeclined` and `votedFor` (group roll-up).

**PRs: threads and comments (create, reply, resolve, file-position comments)** _(confidence: high)_

List threads:
- `GET .../pullRequests/{id}/threads?$iteration=&$baseIteration=`. The two iteration parameters move thread positions onto the diff being shown.
- System messages (votes, pushes) arrive as `commentType: system`.

New thread: `POST .../threads` with:
- `comments: [{content, parentCommentId: 0, commentType: text}]`
- `status: active`
- File comments also need `threadContext {filePath, rightFileStart {line (1-based), offset (0-based)}, rightFileEnd}` (or `leftFile*` for the left side).
- They also need `pullRequestThreadContext {iterationContext {firstComparingIteration, secondComparingIteration}, changeTrackingId}`. `changeTrackingId` comes from iteration changes and is required for PRs with iteration support.

Reply: `POST .../threads/{threadId}/comments` with `{content, parentCommentId}`.

Resolve or reopen: `PATCH .../threads/{threadId}` with `{status: fixed|wontFix|closed|byDesign|pending|active}`.

Evidence: git/pull-request-threads/list, create, update (CommentThreadStatus, CommentThreadContext, CommentPosition, GitPullRequestCommentThreadContext, CommentType); git/pull-request-thread-comments/create (parentCommentId)

**PRs: iterations, changes and getting a side-by-side or unified diff** _(confidence: medium)_

There is no unified-diff endpoint.

1. `GET .../pullRequests/{id}/iterations` returns each iteration's sourceRefCommit, targetRefCommit and commonRefCommit.
2. `GET .../iterations/{n}/changes?$compareTo=0&$top=(default 100, max 2000)&$skip` lists the changed files (page with `nextSkip`). Each entry has changeType, originalPath, changeTrackingId, and `item.objectId` / `item.originalObjectId` (the new and old blob ids).
3. Get both versions with `GET .../repositories/{repo}/blobs/{sha1}?$format=text`, or `items?path=&versionDescriptor.version={commit}&versionDescriptor.versionType=commit&includeContent=true`.
4. Compute the diff in the worker.

Line-level diff blocks:
- The web UI and SDK use the undocumented preview `POST .../repositories/{repo}/filediffs`.
- Body: `FileDiffsCriteria {baseVersionCommit, targetVersionCommit, fileDiffParams [{path, originalPath}]}`.
- Response: `FileDiff.lineDiffBlocks [{changeType none/add/delete/edit, originalLineNumberStart, originalLinesCount, modifiedLineNumberStart, modifiedLinesCount}]`.
- One community client found the response wrapped and blocks running past the end of a file.
- `GET .../diffs/commits` only lists changed paths.

Alternative: run `git diff` in the local clone. A dev workspace usually already has one.

Evidence: git/pull-request-iterations/list (GitPullRequestIteration fields); git/pull-request-iteration-changes/get ($top max 2000; sample has objectId/originalObjectId); git/blobs/get-blob ($format text); git/items/get; git/diffs/get; azure-devops-node-api api/GitApi.ts getFileDiffs (locationId c4c5a7e6-e9f3-4730-a92b-84baacff694b, '7.2-preview.1'); api/interfaces/GitInterfaces.ts LineDiffBlock; github.com/remshams/ado-pr/pull/36 (POST _apis/git/repositories/{repo}/filediffs, 7.1-preview.1)

**PRs: build checks, required reviewers, comment resolution (policy evaluations) and statuses** _(confidence: high)_

Policy evaluations:
- `GET {org}/{project}/_apis/policy/evaluations?artifactId=vstfs:///CodeReview/CodeReviewId/{projectId}/{prId}&includeNotApplicable=&api-version=7.1-preview.1`
- One record per branch policy: build validation, minimum reviewers, required reviewers, comment resolution, linked work items.
- `status`: queued, running, approved, rejected, notApplicable or broken.
- `configuration` identifies the policy type and whether it is blocking. `context` is internal data; for build policies it probably holds the build id.
- Re-run build validation: `PATCH {project}/_apis/policy/evaluations/{evaluationId}` (requeue, vso.code_write).

Other status sources:
- External statuses (e.g. scanners): `GET .../pullRequests/{id}/statuses`.
- The PR object itself carries `mergeStatus`, `isDraft`, `reviewers[].vote` and `autoCompleteSetBy`.
- Status for many PRs costs one PR call plus one evaluations call plus one threads call each. Fetch on demand or cache.

Evidence: policy/evaluations/list (artifactId format, PolicyEvaluationStatus); policy/evaluations/requeue-policy-evaluation; git/pull-request-statuses/list

**PRs: complete, auto-complete, abandon, draft** _(confidence: medium)_

All through `PATCH {org}/{project}/_apis/git/repositories/{repo}/pullrequests/{id}`. The docs list the updatable properties as Status, Title, Description (up to 4000 characters), CompletionOptions and MergeOptions.
- Complete: `{status: completed, lastMergeSourceCommit: {commitId}, completionOptions {mergeStrategy: noFastForward|squash|rebase|rebaseMerge, deleteSourceBranch, transitionWorkItems, mergeCommitMessage, bypassPolicy, bypassReason}}`
- Auto-complete: `{autoCompleteSetBy: {id: me}, completionOptions}`. Auto-complete always waits for required (blocking) policies.
- Abandon: `{status: abandoned}`. Reactivate: `{status: active}`.
- Draft: create with `isDraft: true` (`POST .../pullrequests?supportsIterations=true`); publish with `{isDraft: false}`.

The Learn 7.1 page has no examples for the complete, auto-complete or draft bodies. Those payloads follow the model fields and common client practice.

**Pipelines: listing, Build API vs Pipelines API, timeline, logs, run/retry/cancel, approvals** _(confidence: high)_

Pipelines API (thin):
- List pipelines: `GET {project}/_apis/pipelines`
- List runs: `GET /pipelines/{id}/runs`. This returns the top 10000 runs with no filters.
- Start a run: `POST /pipelines/{id}/runs` with `{resources.repositories.self.refName, templateParameters, variables, stagesToSkip, previewRun}`.

**Rate limits and recommended polling** _(confidence: high)_

Limits:
- 200 TSTU per user in a sliding 5-minute window. One TSTU is a typical user's load over 5 minutes.
- Past the limit, requests are delayed (up to 30 s each), then blocked with HTTP 429 `TF400733`.

Headers, mostly sent before delays begin:
- Retry-After (on an HTTP 200 response)
- X-RateLimit-Resource, X-RateLimit-Delay, X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset, X-RateLimit-Cost

Microsoft's guidance: batch requests, scope queries to a project, avoid Contains/Ever/Not, and keep queries under 30 s. WIQL and per-item GETs are the main cost. There is no official polling interval, so the client should adapt using these headers.

Evidence: learn.microsoft.com/azure/devops/integrate/concepts/rate-limits (TSTU definition, 200 TSTU, header table, TF400733); azure/devops/integrate/concepts/integration-bestpractices

**Push alternatives to polling (service hooks, webhooks, SignalR)** _(confidence: high)_

Neither push option works for a desktop client:
- Service hooks and webhooks send JSON to 'any service that has a public endpoint'. They need inbound IP allowlisting and the Edit/View subscriptions permissions, which only project administrators have by default. A desktop client would need a hosted relay and admin rights.
- No SignalR or live channel is documented.

The plan has to be polling.

Evidence: learn.microsoft.com/azure/devops/service-hooks/overview (IP ranges; 'By default, only project administrators have these permissions'); azure/devops/service-hooks/services/webhooks ('public endpoint'; prerequisites); hooks/subscriptions/create

**Which OAuth scopes do these jobs need?** _(confidence: high)_

Scopes per area:
- Boards: vso.work_write
- PRs and threads: vso.code_write (+ vso.threads_full)
- PR statuses: vso.code_status
- Pipelines run, retry and approvals: vso.build_execute

### Constraints

- Target api-version 7.1 (latest GA). Comments (7.1-preview.4), policy evaluations (7.1-preview.1), Graph search (7.1-preview.1), org teams (7.1-preview.3), Markdown comments (7.2-preview.4) and filediffs (undocumented preview) are preview, so the client must allow a different api-version per call.
- The worker talks to four hosts: dev.azure.com, vssps.dev.azure.com, app.vssps.visualstudio.com and almsearch.dev.azure.com. Any network allowlist has to include all four.
- No documented org-wide PR list. 'My PRs' and 'PRs to review' cost one request per project (or repo) per refresh, filtered by the per-org connectionData id.
- WIQL returns ids only. Loading fields takes extra calls at max 200 ids each. Results are cut off at 20,000 with no error, query text is capped at 32K characters, and queries must finish in under 30 s.
- Board column moves are per team: the WEF_<guid>_Kanban.* field names come from that team's board. System.BoardColumn, System.BoardColumnDone and System.BoardLane are read-only. The sprint taskboard uses its own endpoint.
- No diff endpoint. The worker fetches both blobs per changed file and computes the diff (or uses preview filediffs, or local git).
- No push channel a desktop app can use. Everything is polled within 200 TSTU per sliding 5 minutes, watching Retry-After and X-RateLimit-* headers.
- Every image needs the user's sign-in: avatars, work-item attachments and inline images, and wiki /.attachments images. The trusted worker must fetch them and pass data to the sandboxed panel, which has no network.
- Wiki edits need the page ETag in If-Match (optimistic concurrency). PR descriptions are capped at 4000 characters.
- Microsoft discourages the IdentityPicker endpoint. The documented reviewer search returns Graph descriptors, which must be resolved to identity ids before the reviewer PUT.

### Unknowns

- Whether GET https://dev.azure.com/{org}/_apis/git/pullrequests (no project segment) works for an org-wide list. It is undocumented; the docs mark project as required.
- The exact filediffs route and response wrapper. The SDK only has locationId c4c5a7e6-e9f3-4730-a92b-84baacff694b; a community client used POST _apis/git/repositories/{repo}/filediffs at 7.1-preview.1 and reported a wrapped response.
- Whether PATCHing only WEF_<guid>_Kanban.Column to a column mapped to another state updates System.State by itself, or whether State must be sent too. Also: which column a card lands in when only System.State changes.
- Whether the timeline changeId parameter returns only the records changed since then, and whether a running step's log appears under build logs before the step finishes. Also the REST route of the live feed (getLines, locationId 858983e4-19bd-4c5e-864c-507b59b58b12).
- Whether searchCriteria.reviewerId=<my id> also returns PRs where only the user's team or group is the reviewer.
- Whether one Entra sign-in reaches all three orgs (<primary-org>, <org-b>, <org-c>). This depends on each org's backing tenant, and the user's PAT only works for <primary-org> today.
- Whether branch policies on the published branch block API edits to code wikis.
- Wiki attachment upload encoding: the docs say octet-stream, but community reports say the body must be Base64.
- How many projects and teams <primary-org> has. This sets the cost of the per-project PR fan-out and of resolving team boards.

### Recommendation

Build one Azure DevOps client inside the trusted worker:
- **Base setup:** api-version 7.1, with a preview version set per call where needed. Keep one client per org, keyed by the connectionData `authenticatedUser.id`. Read Retry-After and X-RateLimit-* headers and slow down when they warn.

**Boards**
- Run org-wide WIQL for `@Me`, then load fields with `workitemsbatch` (200 ids per call).
- Read the team's board once (columns, stateMappings, WEF field names) and cache it.
- Move a card with one JSON-patch: System.State, the WEF Column (and Column.Done for split columns) and a `test /rev` op.
- Show HTML or Markdown descriptions according to `multilineFieldsFormat`.

**PRs**
- Lists: fan out once per project with reviewerId or creatorId.
- Opening a PR: load the PR, then iterations, then iteration changes, then both blobs per file, and compute the diff in the worker. Optionally use filediffs, or local git when the repo is cloned in an Orca worktree.
- Load threads and policy evaluations for the status view.
- Votes go through `PUT reviewers/{me}`. Complete, auto-complete, abandon and draft go through PR PATCH.
- For sharing, build the link from `repository.webUrl` + `/pullrequest/{id}`.

**Pipelines**
- Use the Build API: builds list, timeline, logs by line range, stage retry/cancel, and build-level `cancelling` / `retry=true`.
- Use the Pipelines API only to start runs with parameters, plus the approvals API for deploy gates.

**Wikis**
- Use the Pages API with ETag/If-Match for edits and pagemoves for renames.
- Read images from the wiki repo through the Git API in the worker.
- Search through almsearch.

**Refresh strategy**
- Poll more often for whatever is on screen and running; refresh the rest when it gains focus.
- Before committing to the design, check the four runtime unknowns with a read-only token in a spike: org-level PR list, WEF-only moves, timeline changeId, and reach across the three tenants.

## Getting an ADO PR in front of people from an Orca plugin: posting to a Teams channel and pinging a senior dev for approval (status as of Nov 2026)

Office 365 Connectors, including the old Incoming Webhook, stopped working on 18–22 May 2026. The replacement is a Teams Workflows (Power Automate) webhook. Any channel member can create one in about 2 minutes from the template "Send webhook alerts to a channel". It needs no admin and no premium licence, and the URL is the secret. The plugin's Node worker POSTs an Adaptive Card to it. The card appears as the Workflows (Flow) bot, not as the user, and the only reply is a 202 with no delivery confirmation.

Graph can post as the user, with real @mentions and cards, to a channel or a 1:1 chat. Its delegated scopes (ChannelMessage.Send, ChatMessage.Send, Chat.Create, Team/Channel.ReadBasic.All, User.ReadBasic.All) are all marked "AdminConsentRequired: No". It still needs an Entra app registration, and the tenant's consent policy may block an unverified external app. That makes it the high-risk option.

No-setup options work today:
- Add the senior as a required reviewer through ADO (ADO notifies them).
- Use ADO's PR-share email API.
- Open a Teams deep link (https://teams.microsoft.com/l/chat/0/0?users=UPN&message=...) through shell.openExternal, which only accepts https and mailto, so msteams:// is not allowed.
- Use the Share-to-Teams web URL.

Recommendation: build in tiers. Use ADO-native actions and deep links first, add the Workflows webhook for the channel card, and offer Graph only if the tenant allows it.

### Findings

**1. Office 365 Connectors / Incoming Webhooks in Teams: retirement status, dates, replacement** _(confidence: high)_

Retired. The final rollout ran from 18 to 22 May 2026 (announced in the 14 Apr 2026 update), after several extensions: Oct 2024, then Dec 2025, 31 Mar 2026 and 30 Apr 2026. Teams docs (ms.date 2026-10-26) say: "Office 365 Connectors in Teams, including connector-based Incoming Webhooks, were retired in May 2026. To receive webhook requests and post messages in Teams, use the Workflows app." ADO's service-hooks Teams page also says connectors are retired and points to Workflows or the Azure DevOps apps for Teams. That rules out the old route of an ADO service hook posting to a connector URL. Microsoft does not define how old webhook.office.com URLs behave now, so treat them as dead. A separate change also matters: Workflows/HTTP trigger URLs on *.logic.azure.com stopped working on 30 Nov 2025. Current URLs are on *.environment.api.powerplatform.com, can be longer than 255 characters, and the sig part has reportedly rotated.

Evidence: https://learn.microsoft.com/en-us/microsoftteams/platform/webhooks-and-connectors/how-to/add-incoming-webhook (Important banner); https://devblogs.microsoft.com/microsoft365dev/retirement-of-office-365-connectors-within-microsoft-teams/ (4/14/2026 update); https://learn.microsoft.com/en-us/azure/devops/service-hooks/services/teams (Note); https://learn.microsoft.com/en-us/troubleshoot/power-platform/power-automate/flow-run-issues/triggers-troubleshoot (logic.azure.com URL change, 30 Nov 2025)

**2. Teams Workflows webhook: setup, payload, auth, limits, licensing** _(confidence: high)_

SETUP (once, by any member of the channel, e.g. the user): channel ... > Workflows > template "Send webhook alerts to a channel" > pick the team and channel > Save > copy the webhook URL. Other templates are "...to a chat", "...from specific people to a channel/chat" and "...from people in an org to a channel/chat".

PAYLOAD: POST JSON {"type":"message","attachments":[{"contentType":"application/vnd.microsoft.card.adaptive","contentUrl":null,"content":{AdaptiveCard object}}]}. MessageCard payloads are also accepted. Card rules: all Adaptive Card elements work except Action.Submit. The supported actions are Action.OpenUrl, Action.ShowCard and Action.ToggleVisibility, so you get an 'Open PR' button but no interactive approve button. Use msteams.width = "Full" for a wide card.

AUTH: the trigger offers Anyone, Any user in my tenant, or Specific users. With 'Anyone', the URL (with its sig) is the secret and the request must not carry an Authorization header. The tenant-restricted modes need a bearer token with aud https://service.flow.microsoft.com/, plus tid (and oid for specific users). That would mean a second Entra token flow, so use 'Anyone' and store the URL in Orca secrets.

RESPONSE: 202 Accepted with no body. Delivery failures show only in the flow's run history.

LIMITS: about 28 KB per message ("Request Entity too large"). More than 4 requests a second is throttled. Trigger runtime limits are about 4,500 invokes per 5 minutes on the Low performance profile.

IDENTITY: posts appear as the Workflows/Flow bot, and the icon and name can't be changed. Private channels are supported via Power Automate or the Workflows app, though the Teams connector reference still says otherwise.

LICENSING: "Using these templates and the Teams webhook trigger does not require a premium license". The Teams connector is Standard. The tenant must allow the Workflows app in the Teams admin center.

OWNERSHIP: the flow belongs to whoever created it and is orphaned if they leave, unless co-owners are added.

OPTIONAL: a flow built by hand (trigger → 'Post card in a chat or channel') can post as the User (the flow owner) instead of the Flow bot. It can also post as Flow bot to 'Chat with Flow bot' with a Recipient, which could be used to DM a senior, and it can use the 'Get an @mention token for a user' action.

Evidence: https://learn.microsoft.com/en-us/microsoftteams/platform/webhooks-and-connectors/how-to/add-incoming-webhook (setup steps, 28 KB, 4 rps, payload examples, Limitations); https://learn.microsoft.com/en-us/connectors/teams/ (TeamsIncomingWebhookTrigger: auth modes, schema, 202/throttling, Standard tier, Workflows app must be allowed, 20 mentions max); https://support.microsoft.com/en-us/office/send-messages-in-teams-using-incoming-webhooks-323660ec-12ca-40b1-a1d3-a3df47e808c4 (template names, no premium licence); https://learn.microsoft.com/en-us/power-automate/oauth-authentication (aud/tid/oid claims); https://learn.microsoft.com/en-us/microsoftteams/platform/webhooks-and-connectors/how-to/connectors-using (supported card actions); https://learn.microsoft.com/en-us/power-automate/teams/send-a-message-in-teams (Post as Flow bot/User, Chat with Flow bot, @mention token)

**3. Microsoft Graph: posting to a channel and DMing a person (permissions, consent, cards, mentions)** _(confidence: high)_

CHANNEL: POST /teams/{team-id}/channels/{channel-id}/messages needs delegated ChannelMessage.Send. Personal Microsoft accounts are not supported. Application permission (Teamwork.Migrate.All) works only for migration, so the message is always sent as the signed-in user.

DM: POST /chats {chatType:'oneOnOne', members:[me, senior via user@odata.bind]} needs Chat.Create. If the 1:1 chat already exists, Graph returns it. Then POST /chats/{id}/messages needs ChatMessage.Send.

PICKERS: Team.ReadBasic.All and Channel.ReadBasic.All to choose a team and channel, and User.ReadBasic.All to look people up.

CONSENT: the permissions reference (ms.date 2026-09-14) lists every one of these delegated scopes as AdminConsentRequired: No. They are also not on the exclusion list of Microsoft's managed default user-consent policy, which does exclude Chat.Read/ReadWrite, People.Read, Mail.* and similar. In practice it still depends on the tenant:
- Admins can switch user consent off, or limit it to verified publishers plus apps registered in the tenant.
- With risk-based step-up consent, users can't consent to multitenant apps that aren't publisher-verified and were registered in another tenant.
So the plugin needs either an app registered in the <company> tenant, or a verified-publisher app.

CARDS: attachments[] with contentType application/vnd.microsoft.card.adaptive. content is a JSON string, and body.content (html) must contain <attachment id="X"></attachment> matching attachments[].id. Only the OpenUrl card action works without a bot.

MENTIONS: body.contentType html with <at id="0">Name</at>, plus mentions:[{id:0, mentionText, mentioned:{user:{id:<Entra object id>, displayName, userIdentityType:'aadUser'}}}].

TERMS: don't use Teams as a log file; only send messages people will read.

Evidence: https://learn.microsoft.com/en-us/graph/api/channel-post-messages?view=graph-rest-1.0 (permissions table, migration-only app perms); https://learn.microsoft.com/en-us/graph/api/chat-post?view=graph-rest-1.0 (Chat.Create; existing 1:1 chat returned); https://learn.microsoft.com/en-us/graph/api/chat-post-messages?view=graph-rest-1.0 (ChatMessage.Send); https://learn.microsoft.com/en-us/graph/api/chatmessage-post?view=graph-rest-1.0 (Example 2 mentions, Example 3/7 Adaptive Card attachment, OpenUrl note); https://learn.microsoft.com/en-us/graph/permissions-reference (AdminConsentRequired columns); https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/manage-app-consent-policies (Microsoft-managed policy exclusions); https://learn.microsoft.com/en-us/entra/identity-platform/publisher-verification-overview (unverified multitenant apps)

**4. No-API options: deep links, Share to Teams, clipboard** _(confidence: medium)_

DEEP LINK CHAT (documented): https://teams.microsoft.com/l/chat/0/0?tenantId=<tid>&users=<UPN1>,<UPN2>&topicName=<name; group chats only>&message=<precanned text>. users accepts UPNs (email addresses) only. It opens the existing chat, or a draft new chat, with the text prefilled in the compose box, and the user presses Send, so the message comes from them. ADO identities already carry the reviewer's uniqueName/UPN, so no Graph call is needed.

PROTOCOL: Microsoft says https deep links first open a browser chooser page (open in the desktop app, download it, or use web). msteams:// skips that page. However, Orca's shell.openExternal only accepts http:, https: and mailto:, so the plugin must use https and accept the extra browser hop.

CHANNEL DEEP LINK: https://teams.microsoft.com/l/channel/<channelId>/<name>?groupId=<teamId>&tenantId=<tid> (add &ngc=true for private channels). This only navigates to the channel; it can't prefill a message.

SHARE TO TEAMS: officially documented only as the embeddable launcher.js button. Its source builds https://teams.microsoft.com/share?href=<url>&msgText=<at most 200 chars>&preview=true|false&referrer=<host> and opens it with window.open. The resulting web dialog lets the user choose a chat or channel and @mention people. Microsoft says only desktop Edge and Chrome are supported and freemium/guest accounts are not.

MAILTO: openExternal supports mailto:, so 'email the senior' with a subject, body and PR link needs no setup.

CLIPBOARD: the Orca plugin host API has no clipboard method; Orca's own clipboard IPC is not exposed to plugins. Copying a rich (HTML) link from the plugin is unproven.

Evidence: https://learn.microsoft.com/en-us/microsoftteams/platform/concepts/build-and-test/deep-link-teams (ms.date 2026-03-26, chat and channel formats); https://learn.microsoft.com/en-us/microsoftteams/platform/concepts/build-and-test/deep-links (https vs msteams:// handlers); https://learn.microsoft.com/en-us/microsoftteams/platform/concepts/build-and-test/share-to-teams-from-web-apps (launcher.js attributes, msgText 200 chars, Edge/Chrome only); https://teams.microsoft.com/share/launcher.js (builds `${base}?href=...&msgText=...&preview=...&referrer=...`, base https://teams.microsoft.com/share); `orca skills get orca-plugin-authoring --reference references/host-api.md` (shell.openExternal: http/https/mailto, user gesture, host consent; no clipboard method); /Applications/Orca.app/Contents/Resources/app.asar (clipboard IPC only for Orca's own renderer)

**5. ADO-native options** _(confidence: high)_

REQUIRED REVIEWER: PUT .../pullRequests/{id}/reviewers/{reviewerId}?api-version=7.1 with {"vote":0,"isRequired":true}. The docs say "When you create a PR and specify required and optional reviewers, Azure Repos notifies the reviewers" (by email). It also blocks completion until they approve, which is exactly the 'send to a senior for approval' semantics. Draft PRs only notify reviewers that were explicitly added.

SHARE PR: POST .../pullRequests/{id}/share?api-version=7.1 with {message, receivers:[IdentityRef]} "Sends an e-mail notification about a specific pull request". Scope vso.code_write. This is the API behind the UI's More options > Share pull request. It works for individual project members only, not groups.

PR COMMENT @MENTION: this also triggers ADO notifications under the default 'comment added / discussion you're involved in' subscriptions. That is my inference from the built-in subscription list.

AZURE REPOS APP FOR TEAMS: '@azure repos subscribe <repo url>' posts 'PR created' (target main) and other events to a channel, with threaded notifications, PR search and PR URL previews (unfurling) for signed-in users. Creating subscriptions needs Project Administrators or team admin rights. Notifications in DMs are not supported, and ADO and Teams must be in the same Entra tenant. If the app is already in the team, a plain PR link pasted through a deep link or Share-to-Teams unfurls into a rich preview at no cost to the plugin.

Evidence: https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-request-reviewers/create-pull-request-reviewer?view=azure-devops-rest-7.1 (isRequired, vote values); https://learn.microsoft.com/en-us/azure/devops/repos/git/review-pull-requests (ms.date 2026-09-08, reviewers notified); https://learn.microsoft.com/en-us/azure/devops/repos/git/pull-requests (ms.date 2026-09-10, 'Send email pull request notifications', draft behaviour); https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-request-share/share-pull-request?view=azure-devops-rest-7.1; https://learn.microsoft.com/en-us/azure/devops/repos/integrations/repos-teams (permissions, subscribe, compose extension, URL preview); https://learn.microsoft.com/en-us/azure/devops/organizations/notifications/oob-built-in-notifications

**6. Least-friction path for one developer with no admin rights, and what each option costs** _(confidence: medium)_

(a) 'Please review' card in a team channel:
- BEST: a Workflows webhook. Cost: about 2 minutes, once, by the user (a channel member), no admin, no premium, no app registration. The URL is pasted into the plugin and stored in secrets, and the worker POSTs an Adaptive Card (title, repo and branch, author, build status, reviewers, 'Open PR' button). Trade-off: it posts as the Workflows bot, so put 'Requested by <name>' on the card. Whether @mentions render is unconfirmed (see unknowns).
- ZERO-SETUP FALLBACK: Share-to-Teams URL or the channel deep link plus a manual paste. Plain link, or a rich one if the Azure Repos app is in the team.
- HIGHEST FIDELITY: Graph ChannelMessage.Send posts as the user with real @mentions. Cost: an Entra app registration (ideally the same one used for ADO OAuth) plus user consent. That may be blocked by tenant policy, needs admin consent if it is, and adds a team/channel picker.

(b) Pinging a specific senior for approval:
- BEST, NO SETUP: make them a required reviewer through the ADO REST API. The plugin already has ADO auth (vso.code_write), ADO emails them, and the merge is gated on their vote. Optionally add an ADO 'share PR' email with a note.
- PLUS a 'Message in Teams' button: openExternal on https://teams.microsoft.com/l/chat/0/0?users=<senior UPN from the ADO identity>&message=<'Could you approve PR !123: <title> <url>'>. No permissions, the message comes from the user, and it costs one browser hop and a press of Send.
- OPTIONAL: Graph Chat.Create + ChatMessage.Send for a true one-click DM card, at the same consent cost as above.
- AVOID: a Workflows 'Chat with Flow bot' DM. It arrives from a bot, which suits approval asks poorly, and needs a hand-built flow.

mailto: is a universal fallback.

Evidence: Synthesis of the sources cited in findings 2–5; Orca constraints from `orca skills get orca-plugin-authoring` (main page: sandboxed panels have no network; shell.openExternal needs a press on a settled control) and references/host-api.md

### Constraints

- Sandboxed Orca panels have no network, so every POST (Workflows webhook, Graph, ADO REST) must run in the trusted-worker Node main. The panel sends requests to it through plugin.request / orca.panels.handle.
- shell.openExternal accepts only http:, https: and mailto: and needs a press on a settled control. Orca asks before opening a host the plugin hasn't been allowed. msteams:// deep links can't be used, and Teams deep links pass through the browser.
- The Orca plugin host API has no clipboard method, so 'copy rich link' can't be relied on.
- Office 365 Connectors and Incoming Webhooks have been gone since 22 May 2026. ADO service hooks that posted to Teams through connectors are dead, so don't design around them.
- Workflows webhook: Adaptive Card actions are limited to OpenUrl, ShowCard and ToggleVisibility (no Action.Submit, so no in-Teams approve button). About 28 KB per message, 4 requests a second. A 202 means accepted, not delivered. It posts as the Workflows/Flow bot.
- Workflows webhook URLs are bearer secrets. They live on *.environment.api.powerplatform.com (logic.azure.com died 30 Nov 2025), may be longer than 255 characters and may be rotated. Store them in Orca secrets, don't validate the host strictly, and provide 'Test' and 'Replace URL' actions.
- Graph Teams messages can only be sent with delegated permissions from a work/school account (application permissions are for migration only). Without a bot, cards support only the OpenUrl action.
- Graph needs an Entra app registration. A multitenant app from the developer's own tenant that isn't publisher-verified will probably fail user consent in <company> under risk-based step-up consent.
- Teams chat deep links' users= parameter accepts UPNs only. Share-to-Teams msgText is capped at 200 characters and is supported only in desktop Edge and Chrome.
- ADO PR share email reaches individual project members only, not teams or groups.
- The current PAT works only for <primary-org>. Teams and ADO integrations, including the Azure Repos app, need ADO and Teams in the same Entra tenant. <org-b> and <org-c> may sit in other tenants.

### Unknowns

- <company> tenant settings:
- Is the Workflows app allowed in the Teams admin center?
- Which user-consent policy applies: 'Let Microsoft manage', microsoft-user-default-low, or consent disabled?
- Can users register Entra apps?
- Is risk-based step-up consent on?
These decide whether the Workflows and Graph tiers are usable without an admin.
- Whether Adaptive Card msteams.entities mentions (UPN or Entra object id) become real, notifying @mentions when the card is posted through a Workflows webhook as the Flow bot. Microsoft documents this for 'Connectors with Incoming Webhooks', not explicitly for Workflows.
- Whether extra JSON fields in the webhook payload (for example a recipient email) can be read in a hand-built flow, so one webhook could DM any person.
- Whether a sandboxed Orca panel can use navigator.clipboard, or whether the worker may run pbcopy/osascript to place plain or HTML text on the clipboard.
- How Orca's openExternal host consent behaves for teams.microsoft.com and dev.azure.com: a one-time allow, or a prompt every time.
- On this Mac, whether https://teams.microsoft.com/l/chat/0/0 links open straight into new Teams desktop or stop at the browser launcher page. Also whether the default browser is Safari, which Share-to-Teams doesn't support.
- Whether the team's review channel is actually Microsoft Teams (the user said 'probably') and whether the Azure Repos app is already installed there, which would make pasted PR links unfurl richly.
- Whether the senior devs' ADO identities (uniqueName) equal their Teams UPNs, which the deep link and Graph lookups need.

### Recommendation

Model 'Share PR' as a list of pluggable destinations, built in three tiers.

Tier 0 ships first and needs no setup beyond ADO sign-in:
- 'Request approval from…' adds the person as a required reviewer through ADO REST, and can also send ADO's PR-share email with a note.
- 'Message in Teams' opens https://teams.microsoft.com/l/chat/0/0?users=<UPN>&message=<text> through shell.openExternal.
- 'Share to Teams…' opens https://teams.microsoft.com/share?href=<PR url>&msgText=<≤200 chars>.
- 'Email' uses mailto.

Tier 1 is the default for the channel card. The user pastes a Workflows webhook URL per channel (guided steps: channel ... > Workflows > 'Send webhook alerts to a channel'). The plugin stores it in secrets, offers a Test button, and the worker POSTs an Adaptive Card with an 'Open PR' OpenUrl button and a 'Requested by' line. Show 'sent (accepted)', not 'delivered'.

Tier 2 is optional and appears only if the tenant allows it: Graph posting as the user (ChannelMessage.Send, Chat.Create, ChatMessage.Send, Team/Channel.ReadBasic.All, User.ReadBasic.All). Request these as incremental consent on the same Entra app registration used for ADO OAuth, and fall back to Tiers 0 and 1 when consent fails.

Don't build on O365 connectors, ADO service-hook-to-Teams, or msteams:// links.
