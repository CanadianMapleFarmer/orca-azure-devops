# Azure DevOps for Orca: build roadmap

**Spec:** [`docs/superpowers/specs/2026-11-03-azure-devops-plugin-design.md`](../specs/2026-11-03-azure-devops-plugin-design.md) · **Orca floor:** `>=1.4.248`

The spec covers several largely independent subsystems, so the build is split into plans, and each plan ships working, testable software on its own. Each plan starts with the spikes (spec §7) that its own design depends on. A plan's detailed version is written once the plan before it has landed, because those spikes can change interfaces downstream.

ADO is mocked (fake `fetch` fixtures) until the user's test project exists. Then a live pass runs per plan (spec §5.9).

| # | Plan | Delivers | Depends on | Spikes it settles |
|---|------|----------|------------|-------------------|
| 1 | **Foundation** ([detailed](2026-11-03-plan-1-foundation.md)) | Installable plugin with a sidebar hub and an always-on worker (status bar item); connect any org with the Azure CLI (private profile per org) or a PAT; account pinning; boards project and team plus code-project settings; ADO HTTP client with rate-limit handling | — | `az` on the worker's PATH; az account picker; tenant discovery |
| 2 | **Boards** | Polling scheduler; sidebar "My work" (grouped by board column, PR chips, Move to, details with comments and parent); full-tab board custom editor (isolated frame) with drag-and-drop between vertical columns, opened with `editor.open`; collapsed swimlanes; epic filter; "Move to next column?" nudge (off until configured); start a workspace (visible step plus `workspace.create.before/after` hooks); "Start an agent on this item" (`agent.launch`); opt-in agent prompt context (`agent.prompt.before`) | 1 | Backing-file location for full tabs; WEF-only moves; hook timing within 2 s |
| 3 | **PRs and sharing** | PRs tab with release sets (approve all, auto-complete all with saved options); share composer with the reference format and template; destinations: rich-text copy, Teams Workflows webhook, Teams chat deep link, add reviewers; reusable `share` module; status-bar "to review" count | 1 | Rich clipboard per OS; deep-link behaviour; PR fan-out cost |
| 4 | **Pipelines** | Runs list (Mine / Running / Needs me / Failed); full-tab live run view (stages, steps, live log tail, search, errors-only, error summary, open file via `editor.open`, rerun, cancel); environment approvals with Share (reuses Plan 3's `share`) and Approve/Reject; always-on failure and approval notifications; status-bar failure and approval counts | 1, 3 | Timeline change detection; log tail cost within TSTU |
| 5 | **Reviews and wiki (basic)** | "To review" inbox: description, files, read-only per-file diffs, threads, votes, "Check out in Orca"; wiki tree, read, search, edit in Orca's own editor on a git-ignored `.orca-ado/wiki` draft (ruling R3), publish with ETag conflict handling | 1, 2 | — |
| 6 | **Sign in with Microsoft and release prep** | Sign in with Microsoft (Entra auth code + PKCE, loopback; Plan 6 ruling P1) with a client-ID setting, cache in `orca.secrets`; README admin guide for the app registration; optional proxy/CA settings; icon, screenshots, `orca plugin inspect` review; publishing only when the user asks | 1 | Loopback sign-in with Orca's external-link consent |

**Open item (needs the user's ruling):** spec §6's "review requested" and "new comment on my PR" notifications have no row. Plan 5 leaves them out because they need a new setting. One candidate is a small task built on Plan 3's background review poll and Plan 4's notifier.

**Testing environment (spec §5.9):** everything that writes runs against the user's personal sandbox org. The client org is used for read-only checks only.
